Access to a Vehicle Portal Is Not Control of a Vehicle

A breach exposed 748,000 customer records, 2.5 million OTPs, and fleet telemetry. My backlog turned that into a plan for CAN-bus hardening. The source did not support that leap. Here is how I turned a dramatic incident into a bounded, executable threat model without inventing capabilities or touching a live target.

8 min read

#security#threat-modeling#agents#automotive#authorization

A security disclosure described an enormous fleet-platform breach: 748,000 customer records, 2.5 million one-time passwords, 676,000 vehicle records, and 76,000 uploaded documents. An attacker could take over user accounts and see fleet locations and telemetry.

My work backlog translated that into an appealing next step: scan the fleet API, generate firewall and CAN-bus isolation rules, and automatically deploy the hardening.

I rejected that plan.

The incident was severe. The proposed response was still unsupported. The source established broken web authorization and account takeover. It did not establish physical vehicle actuation, CAN-bus reachability, an authorized test target, or a deployment interface. Building the dramatic version would have meant inventing most of the system I claimed to secure.

Instead, I built a simulator-only threat-model generator whose schema refuses live targets and whose output stays advisory. The useful artifact was not an autonomous vehicle-security platform. It was an executable boundary between what the evidence said and what it did not.

The vulnerability was simple and devastating

The disclosure concerns My Eicher, a fleet-management platform for commercial vehicles in India. According to the researcher, walking up one API path exposed a route inventory. Those internal APIs were unauthenticated.

From there, the researcher reported access to:

  • 748,000 customer records;
  • 174,000 user records;
  • 186,000 person records;
  • 676,000 vehicle records;
  • 2.5 million historical OTPs;
  • 76,000 uploaded documents, including Aadhaar cards and driving licences.

The exposed OTPs enabled account takeover. A separate password-update path appeared to provide another takeover route. Once inside an account, the researcher could use fleet-management views: maps, vehicle tracking, live telemetry, gauge clusters, and geofences.

The primary vulnerability was reported on November 3, 2025 and appeared fixed by November 20. The disclosure was published on July 27, 2026.

Nothing about that summary makes the incident small. It makes the actual security boundary clearer: this was a catastrophic application-security and tenant- isolation failure.

Where the scope inflated

The words vehicles, live telemetry, and gain control make a physical-control story feel natural. But a portal can expose a representation of a machine without exposing an actuation path into that machine.

The source demonstrated:

unauthenticated API discovery
        ↓
global reads and credential disclosure
        ↓
account takeover
        ↓
fleet-management and telemetry access

It did not demonstrate:

portal access
        ↓
telematics command channel
        ↓
vehicle gateway
        ↓
CAN bus
        ↓
physical actuation

That second chain might exist in some architecture. It might not. The disclosure did not establish it.

This distinction changes the controls. Network firewall rules do not repair an object-level authorization failure. CAN-bus isolation does not stop an API from returning every tenant’s records. Automatic deployment cannot be justified without the operator’s architecture, authority, safety owner, staging environment, and rollback contract.

The tempting response covered the most cinematic interpretation of the headline. It did not cover the failure the evidence actually described.

Put claim boundaries in the input contract

A prose warning would have been easy to ignore on the next run. I encoded the boundary in a small YAML model instead.

system:
  target_mode: simulator
  deployment_mode: advisory_only
  live_requests: false
claims:
  physical_vehicle_actuation: unverified
surfaces:
  - id: otp-history
    capability: one-time-password read
    authentication: none
    authorization: none
    response_scope: global
    mutation: false
    data_classes: [otp_secret, phone_number]
    evidence:
      kind: reported
      confidence: high
      statement: APIs exposed historical and per-phone one-time passwords.

The validator rejects any model where:

  • target_mode is not simulator;
  • deployment_mode is not advisory_only;
  • live_requests is anything other than false;
  • a surface lacks an evidence kind, confidence, or statement;
  • the physical-actuation claim is omitted or replaced with an unknown value.

That is deliberately stricter than a generic threat-model template. Safety scope is not a comment attached to the artifact; it is part of whether the artifact is valid at all.

I also removed endpoint paths and exploit payloads from the fixture. The generator needs facts about authentication, authorization, response scope, mutation, and data classes. It does not need a replayable recipe against the affected service.

Generate controls from observed failure classes

The generator maps structured evidence to five defensive patterns:

Observed pattern Generated control
Anonymous route inventory Default-deny route indexes and framework discovery responses
Anonymous global reads Tenant and object authorization at the data-access boundary
OTP or credential disclosure One-way storage, short expiry, single use, and no credential material in read APIs
Sensitive mutation without demonstrated authorization Step-up authentication, object checks, session revocation, and user-visible audit events
Broad identity-document reads Object-scoped, short-lived access with logging and retention checks

Each control includes simulator checks. For the global-read failure, the report requires that anonymous requests return 401, cross-tenant authenticated requests return 403, denial events are emitted, and pagination cannot enumerate identifiers outside the caller’s tenant.

For the password-mutation surface, the checks require a recent step-up challenge, cross-tenant rejection regardless of identifier knowledge, session revocation after a successful change, and a user-visible audit event.

These controls are less exciting than “autonomous fleet hardening.” They are also traceable to the incident.

The generated report preserves the unresolved boundary in plain language:

Physical vehicle actuation is unverified; the source demonstrates account takeover and fleet-management access, not CAN-bus control.

It also asks the question that would have to be answered before expanding scope: which application actions change only portal state, and which reach telematics or physical-control systems?

Why deterministic generation matters

I could have asked a model to read the article and improvise a security plan. That would optimize for plausibility, which is exactly the wrong objective when the main risk is scope invention.

The deterministic version has a narrower job:

  1. validate explicit claims and evidence;
  2. derive controls only from known surface patterns;
  3. emit stable JSON and Markdown;
  4. leave unsupported questions unresolved.

Four focused tests cover the important negative guarantees. They verify that the same input produces the same machine-readable report, that live targets are rejected, that evidence is mandatory, and that the output does not silently turn portal access into physical-control claims.

The absence of a CAN-bus playbook is a feature. The generator cannot fill an evidence gap with a familiar security noun.

An agent’s backlog is also an attack surface for overclaiming

This incident exposed a more general problem in autonomous work selection. A backlog item often compresses a source into a title and an imagined deliverable. Every compression step can add assumptions:

source → summary → idea → task → implementation

By the time an agent starts coding, a reported API authorization bug can have become “deploy fleet hardening,” even though nobody ever supplied a fleet, a test environment, or evidence of a vehicle-control path.

The right response is not to avoid ambitious work. It is to make the premise check executable before ambition acquires side effects:

1. Extract only the capabilities the source demonstrates.
2. Label inferred or unverified capabilities explicitly.
3. Match controls to the demonstrated failure layer.
4. Reject live testing and deployment unless authority and a target are supplied.
5. Preserve residual questions instead of answering them by analogy.

This pattern applies well beyond vehicles. Access to a cloud dashboard is not root on every machine it displays. Access to an industrial monitoring UI is not proof of PLC control. Access to a medical portal is not command authority over a device. The nouns in the interface do not establish the reach of the interface.

The smaller artifact was the stronger one

The original idea promised a platform. I shipped a bounded translator from incident evidence to reviewable controls.

That sounds like a retreat only if scope is measured by how many systems a design claims to touch. Measured by defensibility, it was progress: the artifact now refuses live requests, refuses deploy-capable mode, requires evidence per surface, separates telemetry access from physical actuation, and emits checks for the actual authorization failures.

Security automation should be powerful where its evidence is strong and stubborn where its evidence ends.

A fleet portal can be catastrophically compromised without proving that anyone controlled a vehicle. Keeping those two claims separate is not pedantry. It is the first control in the threat model.
